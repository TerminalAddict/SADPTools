# Activation, network configuration and password recovery

Milestone two adds native single-device SADP operations to the desktop and CLI. The Go engine is independent of Wails. Synthetic tests cover the transactions, but hardware results are tracked separately. The user reported successful activation on an IPC-B261H-MU, V5.7.1 build 220610, using the Windows application after the v1.0.2 correction. Network authentication was corrected after DHCP failed on that camera; the new write still requires hardware verification. Support-code recovery remains an unverified legacy implementation. See the [device-management audit](device-management-audit.md).

## Desktop workflow

Discover devices, select one, then use **Activate device**, **Set security questions**, **Configure IP / DHCP**, or **Password recovery** in the details panel. Stop discovery before starting an operation. Review its MAC/serial and the form, then press the named action button to send the request. SADPTools automatically uses an adapter that discovered the device; no adapter selection is needed.

If multiple adapters discovered the device, **Connection options** offers an optional override. Automatic selection prefers the adapter selected for scanning if it saw this device, otherwise the first recorded discovery route. Each device write is sent once through exactly one adapter. Activation first performs a read-only inquiry and encryption-key exchange on that same adapter. Network configuration first performs a fresh inquiry to determine authentication and preserve unrelated settings. If the adapter is no longer available, rediscover to check the connection; commands are never retried through other adapters automatically. The chosen adapter appears in the diagnostic log.

- Activation sets the initial admin password using the SADP encrypted activation profile. A fresh inquiry must report the selected MAC as inactive before a key exchange or write. This profile accepts **8–16 UTF-8 bytes**, with at least two character classes; firmware may impose stricter rules. Longer passwords are rejected rather than truncated. No plaintext fallback is attempted. The GUI, CLI and provisioning engine use the same implementation.
- **Set security questions** configures three recovery questions using the current admin password. It opens automatically after acknowledged single-device activation, with **Set up later** available, and can also be opened for an active camera. Saving remains a separate click. The supported native SADP profile works without web connectivity and reads back configured question IDs after saving. Existing questions require replacement confirmation. See [setup, encryption, compatibility and testing](security-question-setup.md).
- Network configuration sends the requested IPv4 address, subnet mask, gateway, SDK command port and DHCP setting using the camera’s advertised authentication profile, never a plaintext password. It preserves the freshly advertised HTTP port, IPv6 settings and SDK-over-TLS port. Missing authentication or incomplete advertised settings stop before the write. Salted authentication currently supports the admin account with passwords up to 16 UTF-8 bytes; longer passwords are rejected, never truncated. The SDK port is not the HTTP port. Values come from discovery; missing fields remain empty and must be supplied. DHCP status that was not advertised must be selected explicitly. Gateway `0.0.0.0` means no gateway. When enabling DHCP, the form still sends the stored static values. Network changes may interrupt recorders or other clients.
- **Experimental legacy support-code recovery** can request data and save it privately. Its copied command formats have not been verified on hardware and do not implement modern encrypted support-code recovery. An empty `exchangecode` is not a complete key exchange; do not interpret that command’s existence as proof of recovery support. Prefer the camera’s web interface or manufacturer tool for this workflow. Obtain a valid recovery code through the device's authorised support process, select the matching submission method, then supply the code and a new admin password. Recovery data is not a reset code generated by SADPTools.
- **Security questions** checks for three configured questions on a reachable camera, displays its question text and submits an encrypted reset after explicit confirmation. Unlike the SADP commands above, this uses detected HTTP/HTTPS and automatically follows the OS route, which can use a gateway or a different adapter from discovery. The camera need not share the computer's subnet. See the [security-question recovery guide](security-question-recovery.md) for the GUI/CLI flow, supported protocol profile and validation limits.

The result distinguishes an explicit device acknowledgement, rejection, and an unconfirmed outcome. After a write, choose **Close and rediscover** to observe the current device state. The inventory is not changed optimistically. **Stop waiting** cancels the receive operation; it cannot undo a request already delivered. No action is retried automatically.

## CLI

The command shape matches the reference tool, with an explicit adapter to avoid sending changes on unrelated networks:

```sh
./bin/sadptools interfaces
./bin/sadptools send --help
./bin/sadptools send 0.0.0.0 activate --help
```

For an inactive device, read the password without putting it in shell history or process arguments:

```sh
read -r -s -p 'New admin password: ' SADPTOOLS_INPUT_PASSWORD
printf '\n'
printf '%s' "$SADPTOOLS_INPUT_PASSWORD" | ./bin/sadptools send 0.0.0.0 activate \
  --mac 'DEVICE_MAC' --interface 'ADAPTER_NAME' --password-stdin --timeout 10s
unset SADPTOOLS_INPUT_PASSWORD
```

Replace `DEVICE_MAC` and `ADAPTER_NAME` with the actual discovered device and adapter. The positional IP is an informational hint; `0.0.0.0` is accepted when unknown. **The MAC is authoritative.** The request is sent using multicast on the selected adapter, so being outside the host's IP subnet does not itself prevent sending.

Inline `--password` is supported for compatibility with the example in the reference project, but it exposes the value to shell history and process listings. `--password-env VARIABLE` reads an explicitly named environment variable. No credentials are taken from persistent settings. Stdin accepts one line, strips only its final newline and preserves spaces in the password.

Network update (use actual values; the following contains placeholders):

```sh
./bin/sadptools send 0.0.0.0 update --mac 'DEVICE_MAC' --interface 'ADAPTER_NAME' \
  --ip 'NEW_IPV4' --mask 'SUBNET_MASK' --gateway 'GATEWAY_OR_0.0.0.0' \
  --port SDK_PORT --dhcp=false --password-env SADPTOOLS_PASSWORD --timeout 10s
```

Provide all network fields deliberately. `--dhcp=true` enables DHCP; the default is false. The command rejects noncontiguous masks, network/broadcast addresses, invalid gateways and missing SDK ports. This implementation accepts subnet prefixes /1 through /30.

Recovery:

```sh
./bin/sadptools send 0.0.0.0 exchangecode --mac 'DEVICE_MAC' --interface 'ADAPTER_NAME' --json
./bin/sadptools send 0.0.0.0 resetpassword --mac 'DEVICE_MAC' --interface 'ADAPTER_NAME' \
  --code-file /private/path/support-code.txt --password-env SADPTOOLS_NEW_PASSWORD --timeout 10s
```

`getencryptstring` and `getencryptstring_v31` are alternative data requests. `securitycode` is an alternative code-submission format; choose the method required by the device/support provider. No method is tried automatically after another fails. `--code-file` accepts a single plain-text code, not an encrypted vendor XML file; `--code-env VARIABLE` is also available. Treat JSON output containing recovery data as private.

Append `--dry-run` to validate and print a redacted plan without opening a socket. It still validates credential inputs, but never prints their values. `--debug` logs operation metadata only. `--json` emits a structured result with `sent`, `outcome`, `message`, and any recognised numeric device error code or requested recovery data.

Additional CLI exits: **4** device rejection, **5** unconfirmed outcome, **130** cancellation (check the result's `sent` flag). A send error is conservatively unconfirmed because delivery cannot be ruled out. Exit **0** for a write means a matching explicit success reply, not an independent verification of the new device state.

## Protocol and compatibility boundaries

Requests adapt the MIT-licensed [reference command templates](https://github.com/cameronnewman/hikvision-tooling/blob/afa00e3db11bb47914e1f0d724c6975e0a41e218/internal/sadp/commands.go): `activate`, `update`, `exchangecode`, `getencryptstring`, `getencryptstring_v31`, `resetPassword` and `securityCode`. XML is encoded using Go's encoder, including passwords with XML metacharacters. No reference executable is used.

One wildcard UDP/37020 socket joins one selected multicast interface; requests go to `239.255.255.250:37020`. Desktop discovery and configuration exclude each other, including automatic scans. Separate processes receive a port-conflict error rather than sharing the socket. Legacy recovery replies require the selected receive interface, matching normalized MAC, echoed UUID and matching command type. Activation and network replies have explicitly bounded exceptions for MAC-less acknowledgements, described below. Unrelated discovery packets, duplicate/nested XML fields and unknown results never imply success. A `Result` of `success` acknowledges a write; known rejection strings or nonzero numeric error codes reject it. Device-provided free-text errors and raw replies are not displayed or logged because they may echo secrets.

Unlike the reference's broad multicast/broadcast sending and substring matching, each write is sent once on one interface and requires an unambiguous reply. Firmware that does not echo the UUID/type, requires broadcast, or uses an unsupported encryption/reply profile may time out or remain unconfirmed. We have not invented numeric success-code mappings or added automatic protocol fallbacks.

The experimental legacy support-code recovery formats still contain plaintext passwords/codes inside XML. Activation negotiates encryption, and network updates use the authentication profile advertised by a fresh inquiry; that unauthenticated local protocol still belongs on a trusted management network. Operation credentials are never put in settings, inventory, ordinary exports or logs. Request buffers are cleared, and GUI fields are cleared on submission/close, but Go/JavaScript strings cannot promise complete memory erasure. Recovery data is returned only to the requesting UI/CLI and saved only when explicitly requested. The desktop export is `sadptools-recovery-v1` JSON, **not** a Hikvision SADP encrypted XML export.

### Encrypted activation correction

The original implementation copied the upstream activation envelope but omitted its required encryption exchange. It also required a MAC in every reply. A read-only investigation on 28 October 2026 with an **IPC-B261H-MU, V5.7.1 build 220610** confirmed inactive status and a successful `exchangecode` response containing only `Uuid`, `Types`, `Result` and `Code`. No password or activation write was sent in that investigation. The response decrypted successfully to the supported 32-byte hexadecimal ASCII challenge. No real challenge, credential or network capture is committed.

The corrected transaction has three stages, all within the requested timeout:

1. Fresh `inquiry`: require the exact MAC, echoed UUID, selected receiving adapter, valid source IPv4 and explicit inactive status. Pin the source IP for subsequent replies.
2. `exchangecode`: generate an ephemeral RSA-1024 key (exponent 65537); send base64 PKCS#1 DER public key in `Code`. Require matching source, adapter, UUID, type and explicit success. A missing MAC is allowed here; a conflicting MAC is rejected. Decrypt base64 RSA PKCS#1 v1.5 ciphertext and validate the challenge without exposing it as recovery data.
3. `activate`: use the first 16 **ASCII** challenge bytes as the AES-128 key and plaintext prefix, append the password zero-filled to 16 bytes, AES-ECB encrypt both blocks, and send base64 ciphertext. This differs from the HTTP ISAPI format: do not hex-decode the challenge or hex-encode the ciphertext. Use a fresh UUID and one transmission. Match its acknowledgement to the pinned source/adapter, UUID and type, with the same MAC rule. Recognise `riskPassword` and `hasActivated` as explicit rejections.

`sent: false` means the activation write was never attempted, even if inquiry or key exchange occurred. Failed preparation reports **Activation was not sent**. Cancellation, send errors or missing acknowledgements after the activation send remain unconfirmed and never cause a retry. The inventory changes only through observed replies: rediscovery or the fresh inquiry in the subsequent security-question setup step.

Wire research used [published SADP activation packets](https://ipcamtalk.com/threads/what-encryption-do-hikvision-cameras-use.39111/) and the publicly archived [SADP library reference](https://github.com/themactep/hiktools/blob/4ba69e93ed68f0b3a0b5839a01bb0580bb8bfa17/gists/libsadp.so) (SHA-256 `52bbb97c9445f4fc7aa4933b0a7619b2d75ec59f54583cf1e6907bf3afb0ad87`). Only protocol behaviour was examined; no SDK binary or proprietary implementation is linked, copied into this repository or distributed. The native implementation uses Go's standard cryptographic libraries. A synthetic vector was independently compared with the reference's encryption routine and standard AES-128-ECB. Automated tests cover the exchange, bounded password encoding, malformed challenges, source/adapter/UUID/MAC/type correlation, explicit rejection, cancellation and lost acknowledgements. **The user subsequently reported successful activation using the Windows GUI. This is user-reported hardware success, not an independent login test or proof of compatibility with other models.**

Hikvision documents multiple recovery workflows requiring device-specific exports and support responses. See [Hikvision's recovery instructions](https://pro-av.hikvision.com/es-la/support/how-to/faq/how-to-reset-password/) and [SADP manual](https://legacy.hikvision.com/sites/default/files/manual/sadp_user_manual.pdf). Security-question recovery now uses a separate local ISAPI implementation; see its [compatibility limits](security-question-recovery.md). Vendor XML import/export, GUID recovery, email recovery, legacy serial/date reset-code generation, authenticated password changes and additional encrypted SADP variants are not implemented. A code accepted by one firmware may not be accepted by another. This milestone does not add reboot, factory restore, cloud unbinding or batch writes.

### Authenticated network-update correction

The former `update` implementation sent the admin password directly, omitted the HTTP/IPv6/SDK-over-TLS fields, and required a MAC in every acknowledgement. On 28 October 2026, a read-only inquiry of the now-active IPC-B261H-MU confirmed `Encrypt=true`, a 64-byte `Salt`, and `DHCP=false`. That matches the authenticated network profile rather than the upstream plaintext template.

The corrected transaction uses one adapter and one timeout:

1. Send a read-only `inquiry` with a fresh UUID. Require that UUID/type, adapter, exact MAC, and a valid source IPv4 matching the advertised address. Require explicit active status and an advertised supported `Encrypt` value. Keep `Salt` only in an ephemeral profile, outside inventory/preferences/logs.
2. Preserve the advertised HTTP port and any IPv6/SDK-over-TLS fields. Missing HTTP port, malformed preserved fields or incomplete IPv6 groups fail before a write; unknown fields are never filled with defaults.
3. Generate a new UUID. With a nonempty 64-byte salt, calculate lowercase hexadecimal SHA-256 of `admin || salt || password`, then raw MD5 of that 64-byte ASCII result. Without a salt, calculate raw MD5 of the password. The salted profile is bounded to 16 password bytes, matching the examined SDK. These legacy algorithms are protocol requirements, not a design for password storage.
4. If `Encrypt=true`, AES-128-ECB encrypt 64 bytes containing `digest[16] || ";" || UUID[36] || zero[11]`, using the digest as key. Base64 the raw ciphertext. If the device explicitly advertises `Encrypt=false`, base64 the raw digest instead. Set `Password` attribute `bSalt="true"` only for salted profiles. Never send the password directly or retry with a weaker profile.
5. Send `update` once with lowercase hyphenated MAC, `PWErrorParse=true`, requested settings and preserved settings. Match UUID/type and adapter. An exact MAC may identify a reply from a newly assigned DHCP address. Without MAC, accept only the source pinned by the fresh inquiry or the explicitly requested new static address; an unknown DHCP address does not establish identity.
6. Interpret `PasswordError`, `locked`, and `notActivated` as explicit rejections. A matching success acknowledges the request; only rediscovery establishes observed DHCP/address changes. Lost replies or errors after sending remain unconfirmed and never cause a retry.

The encoding was independently checked using **synthetic inputs only** against the archived library’s digest and AES routines under isolated emulation. [NKSC’s published camera analysis, tables 14–15](https://www.nksc.lt/doc/en/analysis/2020_06_09_Hikvision-Dahua.pdf) also documents discovery authentication fields and `Password bSalt="true"` in network updates. The same [archived SDK reference](https://github.com/themactep/hiktools/blob/4ba69e93ed68f0b3a0b5839a01bb0580bb8bfa17/gists/libsadp.so) used for activation supplied protocol behaviour; no SDK code or binary is included in SADPTools. Tests contain synthetic salted/unsalted, encrypted/digest-only vectors, preserved-setting checks, invalid profiles, correlation checks and no-retry checks. A fresh **read-only** camera check accepted its actual profile and encoded a request **offline using a synthetic password**; no authentication attempt or network write was sent.

## Physical-device acceptance checks

Use a spare authorised device and record its firmware before testing. Confirm activation with a password containing XML metacharacters; verify login separately. Change IPv4/mask/gateway/SDK port, rediscover by MAC, then test DHCP enable/disable and restoring the original network configuration. Check incorrect-password rejection and device lockout behaviour without repeated attempts. Exercise a legitimate recovery-data/code cycle with support. Verify both a success reply and rediscovered state, and test a lost acknowledgement without automatically resending the write.

Repeat on Windows 10/11 with the offline installer, multiple adapters and firewall profiles. Linux compilation, synthetic tests and GUI inspection cannot establish physical-device compatibility or Windows socket behaviour.
